# Bump deps

One pass over a project's direct dependencies: the bumps the ecosystem vouches for land as a single commit, and every jump that means real work becomes a researched ticket the implement flow can pick up. The run is *gather → ask once → execute → report*; the **stop** — one interruption after the research is in — is the only moment the user is at the keyboard.

The **manager** is the package manager the project's lockfile and manifest name. Every listing, resolution, and update command is the manager's own, proven by running it in this project before the run relies on it — nothing carried over from another ecosystem. Transitive-only updates are out of scope: judgment applies to the declared surface.

A **boundary** is a bump the versioning convention doesn't vouch for: a major, any bump of a 0.x version, or any bump in an ecosystem whose convention doesn't promise compatibility. Everything else is a **batch** candidate. Research **promotes** a boundary into the batch; a red check **demotes** a batch member to a boundary.

The **tracker** is whatever `docs/agents/issue-tracker.md` describes; without the file, local markdown: `.scratch/bump-deps/issues/<NN>-<slug>.md` with a `Status:` line and a `Blocked by:` line. Tickets posted to a shared tracker open with `> *This was generated by AI during a bump-deps run.*`

Arguments scope the survey to named packages; empty means every direct dependency.

## 1. Survey

**Gate**: working tree clean; failing it ends the run, reported per step 7.

Detect the manager and the repo's own check commands, then list the outdated direct dependencies in scope, installed → latest stable each.

Done when every outdated in-scope dependency is listed with both versions — or the list is empty, which ends the run with that as the report.

## 2. Classify

Sort the list: batch candidate or boundary, by the definition above. Doubt about whether the convention holds for a package is itself a boundary verdict.

Done when every listed dependency carries exactly one classification.

## 3. Research

Per boundary, establish what changes between installed and target touch *this* codebase. Use the `research` skill when the session has it; otherwise read the primary sources — changelog, release notes, migration guide — inline and write the artifact the research skill would have left: a cited markdown file in the repo, at `.scratch/bump-deps/research/<package>.md` when no convention says otherwise. Either way the file records only changes with a footprint in this codebase, each naming the affected files or symbols.

A boundary whose research finds no affected surface promotes into the batch, its file kept as the audit trail.

Done when every boundary has a research file and is either promoted or carries its list of required changes.

## 4. The stop

One stop covering everything — as many `AskUserQuestion` calls back-to-back as the decisions need, but the user sits down once: the batch as proposed — the user confirms or edits membership — and, per surviving boundary, the decisions its changes force (adopt the new API or shim it, replace a dropped feature, take the migration path or a different library). A repo with no check commands adds one more question: land the batch unverified, or leave it unapplied. A decision the user defers is recorded as deferred; it blocks the ticket in step 6, it does not stall the run.

Done when batch membership is confirmed and every boundary decision is answered or deferred.

## 5. Bump

A stop verdict of leave-unapplied skips this step, the report saying so. Otherwise: branch to `deps/<yyyy-mm-dd>`, suffixed `-2`, `-3`… when the name is taken. Apply the confirmed batch with the manager's update commands and run the check commands from step 1. Red: bisect the batch to the culprit, demote it with the observed failure attached, re-run until green. A demotion is final for the run: the dependency goes to step 6 as a boundary. Leave the surviving batch as exactly one commit, message listing the bumps — marked unverified when the stop chose to land it without checks. Do not push.

The run ends at green checks: runtime behaviour stays the user's to test by hand, and the report says the app has not been seen running.

Done when the checks pass on the committed batch — or the stop chose unverified, or nothing survived, either of which the report says plainly.

## 6. Ticket

Per unpromoted boundary, create a ticket the tracker's way. It carries: installed → target, the research file linked, the required changes, and the user's decisions from the stop written in. A boundary demoted in step 5 carries the observed failure in place of a research file, and its decisions — never asked at the stop — count as deferred. When one boundary must land before another — peer ranges, a shared framework — the dependent ticket records that as `Blocked by:`.

A ticket whose decisions are all answered is marked agent-ready for the implement flow. A deferred decision instead sits under a `## Decisions needed` heading and keeps the ticket off agent-ready until the user answers it there.

Done when every unpromoted boundary has a ticket whose readiness matches its decisions.

## 7. Report

Finish with one table, a row per dependency the survey listed: bumped (in the commit), promoted (research found no surface, file linked), ticketed (ticket ref, ready or awaiting decisions), or demoted (what went red, ticket ref). Below it: the branch name and that it is unpushed, which checks passed — or that the batch landed unverified — and that runtime is untested. On a gate failure: where the run stopped, what it saw, the one thing that unblocks a re-run.

Done when every dependency the survey listed appears in exactly one row and the user has the summary.
